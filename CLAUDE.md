# Claude Code — Obsidian PM

This repository is a working Obsidian vault: the system behind it (`Config/`: templates, Templater scripts, tests, bases) plus made-up sample notes that demo it. The class files in `plugin/src/commands/`, `startup/` and `shared/` run as **Plainday**, the plugin built from them (`plugin/`, with `manifest.json` and `package.json` at the root). They ran through the CustomJS plugin before Plainday and lived in `Config/Scripts/CustomJS/` until OBS-270; the `customjs-final` tag is the last version that runs under CustomJS (OBS-257). `README.md` says how to install it, and `Config/Manual.md` how it works: the notes, the lines in a daily note, and what every command and script does. Before editing a daily or monthly note, read the manual's *Rules for agents*.

Personal instructions (where a maintainer's own vault is, how it pulls updates, backups) belong in `CLAUDE.local.md`, which git ignores. Read it if it exists.

## Obsidian CLI

The `obsidian` CLI talks to the running Obsidian app. With more than one vault open, **always name the vault, before the command**: `obsidian vault=<folder name> open path="Welcome.md"`. Put after the command, `vault=` is silently ignored and the command goes to whichever vault Obsidian picks.

- `obsidian vault=<v> open path="<vault-relative-path>"` opens a file.
- `obsidian vault=<v> search query="<text>"` searches the vault.
- `obsidian vault=<v> command id=plainday:<id>` runs a command, such as `plainday:add-note`. The ids are in `plugin/src/commands/index.js`.
- `obsidian vault=<v> eval code="plainday.SnapshotDailyNotes.invoke()"` calls a class that isn't a command.
- `obsidian vault=<v> plugin:reload id=plainday` reloads the plugin after a new `main.js` is copied in.

For reading notes, `grep` on the markdown files is often faster.

## Working on the system

- **PR flow:** make each change on a branch in a git worktree **outside** this folder, for example `git worktree add ../obsidian-pm-<slug> -b <branch> origin/main`. Run the tests, push, and open a PR. Merge only when the maintainer says so. Afterwards, delete the branch and the worktree.
- **Testing in Obsidian:** this clone is the one **dev vault** (Obsidian opens it as `obsidian-pm`), and one PR is tested in it at a time, by the maintainer. Never check a branch out in a vault that's in daily use, and never switch the dev vault on your own: commit on the branch, push, open the PR, write the test plan note (Empty Note frontmatter, a checklist linking the sample notes each step uses, a *Notes for Claude* section at the end; `CLAUDE.local.md` says where it goes), and say the PR is ready. When the maintainer says go, run `"Config/Scripts/dev-vault.sh" test <branch> --plan <note>` from this folder. It checks the branch out detached (the worktree holds the branch), builds Plainday from it in `.dev-vault/build/` and copies it in, reloads it (or turns it on), or the vault when a settings file changed, and opens the plan as `<ISSUE> Test Plan.md` at the vault root. It refuses a commit without `manifest.json` (from before Plainday), while another issue holds the lock (`.dev-vault/testing`), or while the tree has changes and `done` hasn't run; the issue that holds the lock can run it again after a fix. Afterwards, `dev-vault.sh done` restores every tracked note, removes the plan and the lock, and returns to a pulled `main`; `status` says where things stand. `done` waits for the app to stop writing before it reports: a reload can set the startup report going, and UpdateObsidianPM won't install from a tree that isn't clean.
- **Never commit from this folder.** The script installs a pre-commit hook that refuses it: while a branch is under test, the scripts, the editor and the calendar sync rewrite tracked notes here, and nothing checks them for real data. Commits come from worktrees; `done` restores this tree.
- **Plainday's build:** npm runs only in a worktree or CI, never in this folder: Obsidian indexes the vault, and `node_modules` would put thousands of files into it (`plugin/preinstall.mjs` refuses). In a worktree, `npm ci` once, then `npm run build` writes `main.js` at the root (git ignores it), and `npm test` tests the bundle. `PLAINDAY_OUT=<folder> npm run build` also copies `main.js` and `manifest.json` into a test vault's `.obsidian/plugins/plainday/`.
  - **The class files are modules, sorted by what starts them** (OBS-271): `plugin/src/commands/` holds the classes a command runs, `startup/` the startup scripts, which start with Plainday and act on their own, and `shared/` the ones only other classes call. Each folder's `index.js` imports its classes and lists them in `CLASSES`; `commands/index.js` also holds the command list, and `startup/index.js` the order the startup scripts run in (`STARTUP`). CI fails a class file in the wrong folder or missing from its index (`.github/ci/checkScripts.mjs`).
  - **A class file's shape** (`plugin/classShape.mjs`): its imports, one per line, `import { a, b } from "<module>";` or `import * as x from "<module>";`, from `obsidian`, `../host.js` or one of CodeMirror's three modules; then `export default class <Name>`, and nothing else. No default import, no renaming, and no import of another class file: the classes reach each other through `plainday` (`plainday.Schedule`), which `plugin/src/host.js` exports with `app`, so there's no import cycle. `plainday.plugin` is Plainday while it's loaded (to add an editor extension, or to check that Plainday is still loaded). The build stops on a file without the shape, and on a line that reaches for the CustomJS plugin, its global or `customJS`, naming the line (`plugin/esbuild.config.mjs`).
  - **A new class** goes in the folder its kind says and into that folder's index. **A new command** goes in `plugin/src/commands/index.js` (an id that never changes once set, a sentence-case name, and an icon of its own from Obsidian's set that the manifest's oldest Obsidian already has); CI checks that it names a class in `commands/`, and the bundle test that its icon is there and not another command's.
- **Lint:** `npm run lint` in a worktree runs Obsidian's lint (`eslint-plugin-obsidianmd`'s recommended config, the rules the community directory's scan runs) on Plainday's code in `plugin/src/` (the class files included), the Templater scripts, the rest of `Config/Scripts/`, `manifest.json`, `package.json` and `LICENSE` (`eslint.config.mjs`). CI runs it in the *Plugin* job.
  - **What the scan reads:** only the files `jsconfig.json` includes, always with type information (OBS-265): `plugin/src/` and `Config/Scripts/Templater/`. A file it leaves out isn't reviewed at all, so a new folder of code goes into `jsconfig.json`. The lint reads those files with type information too, from Obsidian's types (the `obsidian` package), and runs Obsidian's rules that need it, such as `no-unsupported-api`, which fails a call to an API newer than the manifest's `minAppVersion`. The class files reach Obsidian through typed imports, so the rule sees their calls too (OBS-271). typescript-eslint's own type checks run on Plainday's own files only (`plugin/src/main.js`, `host.js` and the three indexes): the scan's `no-unsafe-*` warnings on the class files, which have no types, wait until they do (OBS-269). `no-undef` runs in `plugin/src/`, whose files import what they use, and stays off for the Templater scripts, which read Templater's globals.
  - **What fails:** any error the baseline doesn't let through, in any file, and any warning in Plainday's own code (`plugin/src/` but the class files, the manifest, `package.json`, `LICENSE`). Warnings in the class files and the Templater scripts never fail; the *Plugin* job's summary counts them by rule (OBS-203 decides what happens to them).
  - **The baseline,** `.github/ci/eslint-suppressions.json`, lists the errors the class files and the Templater scripts had when the lint started, as a count per file and rule. A PR that fixes one fails with "There are suppressions left that do not occur anymore" until `npm run lint:prune` takes it out, and from then on that error can't come back. A PR that renames a file with entries moves them to the new name by hand.
  - **Never at the root** (OBS-268): ESLint reads an `eslint-suppressions.json` from the folder it runs in without being asked, and the community directory's scan runs it at the root with its own rule levels, under which some baseline errors are only warnings. ESLint then stops with "There are suppressions left that do not occur anymore", and the scan reviews nothing. So the baseline lives in `.github/ci/`, every command that reads or writes it names it with `--suppressions-location .github/ci/eslint-suppressions.json` (`npm run lint` and `lint:prune` do), and `checkBaseline.mjs` fails on a file at the root.
  - **Never re-record the baseline** (`--suppress-all`) to get past a failure: CI fails when any rule lets through more errors than on `main` (`checkBaseline.mjs`). The one exception is a PR that updates a lint package (the lint plugin, ESLint, typescript-eslint, TypeScript or Obsidian's types), since a new version can find new things. It re-records the baseline with `npx eslint --quiet --suppressions-location .github/ci/eslint-suppressions.json . --suppress-all` (without the location, ESLint writes a new file at the root) and says in the PR what changed.
  - **Pinned versions:** the lint plugin at exactly 0.5.1, since Obsidian changes it often and the scan with it; TypeScript 5, since the lint plugin can't use TypeScript 7; ESLint 10; Obsidian's types (`obsidian`) exactly at the newest version, since `no-unsupported-api` reads each API's version from them and older types don't know the newer APIs, with the two CodeMirror packages they ask for. Updating one is a PR of its own.
- **Releases:** a GitHub release per version, tagged with the manifest's version exactly (`0.0.2`, no `v`), with `main.js`, `manifest.json`, and `styles.css` once the repository has one. BRAT installs from it, and the community directory lists it. A release is cut when the maintainer asks for one; between releases, the maintainer's own vaults take a build of `main` without one (OBS-234).
  - **To cut one,** in a worktree: `npm version 0.0.2 --no-git-tag-version` raises the version in `package.json`, its lockfile, `manifest.json` and `versions.json` (`plugin/version-bump.mjs`), and makes no commit or tag. Commit, push and open a PR. Its *Plugin* job's *Release dry run* says "Merging publishes 0.0.2" (only when the PR raises the version past `main`'s), and keeps the files for a week to download (`npm run build && node .github/ci/release.mjs dry-run` says the same locally). Merging the PR publishes the release (`.github/workflows/release.yml`): the workflow builds the merge commit afresh, tags it, attaches the files, and lists the PRs merged since the previous release as its notes.
  - **CI checks the version** (`checkVersion.mjs`): the four files agree, it's three numbers, and it isn't lower than `main`'s. Plainday stays at 0.0.x until the listing, which submits 0.1.0 (OBS-207).
  - **Check the result:** the release on GitHub has its files, and BRAT installs it into a throwaway vault.
  - **A merge that doesn't raise the version** publishes nothing, even when that version has no release, so a release deleted on purpose stays deleted (OBS-266). If publishing fails, that version still has no release, and the next merge won't publish it: run the *Release* workflow again by hand (*Actions*, *Release*, *Run workflow*), which publishes `main`'s version when it has no release.
- **Tests:** run `node --test "Config/Scripts/tests/*.test.mjs"` from the repo root, and `npm test` for the bundle.
  - **How a test loads a class:** Node can't run a class file's imports (Obsidian's package carries only types), so the tests read it through `plugin/classShape.mjs`: `classScript("schedule.js")` is the file as a script whose imports read their names from the vm context's globals, and `loadClass("schedule.js", context)` runs it there and returns the class. A test gives its stand-ins by name (`moment`, `Notice`, `MarkdownView`, `app`, `plainday`), and swaps one by setting it on the context. It needs no npm, so CI's test job runs plain Node.
  - `demoVault.test.mjs` checks the sample notes against the scripts: the committed time reports must equal what the scripts render, and every link and `parent` must be right. If a change alters what the report writes, re-render the sample notes with `node "Config/Scripts/tests/demo/renderReports.mjs"` and commit the result.
  - Checks against a real vault's data go in `*.private.test.mjs` files with `*.private.json` fixtures, which git ignores.
- **Speed:** a change that adds work on every keystroke (an editor extension) or on vault events stays within the speed budget: each feature adds at most 1 ms per keystroke, everything the system adds at most 2 ms, and the cost doesn't grow with note length. Background work on a save or metadata event is debounced and stays under 10 ms. Measure it and put the numbers in the PR. Until `dev-vault.sh perf` does it (OBS-92), measure by hand:
  - **In a throwaway vault, never the dev vault:** a scratch folder with the branch's Plainday build and invented notes.
    - The CLI can't open a folder as a vault. From any open vault, `obsidian vault=<open vault> eval code="require('electron').ipcRenderer.sendSync('vault-open', '<folder>', false)"` does.
    - `eval` only exists in a vault with community plugins allowed (`plugins:restrict off`).
    - It runs in the app, so it needs Obsidian running and can't run in CI.
  - **What to time:** type 100 characters and delete them inside a line the feature draws, calling the editor's `measure()` after each edit so layout counts.
    - Do it in a 150-line note and a 3,000-line note.
    - Take the best of three runs, with the feature's extension removed and then back.
  - **A background window doesn't repaint.**
    - Screenshots go through `dev:cdp method=Page.captureScreenshot`.
    - `dev:cdp method=Emulation.setFocusEmulationEnabled` makes the editor count as focused, which Live Preview needs before it opens a link for editing.
- **Docs:** a change a user would notice updates `Config/Manual.md` in the same PR, `README.md` too when it changes installing or the overview there, and the sample notes if they should show it. The manual is the full description, the README a front door that points at it; don't copy the manual's detail into the README. Before opening the PR, read each manual and README section that names a changed script against the diff and fix what no longer matches: CI checks that the docs were touched, not that they are right.
- **CI (`.github/workflows/ci.yml`)** runs on every PR and must be green before a merge. It runs the tests, builds Plainday, runs its bundle tests and Obsidian's lint, and says what merging would release (the *Plugin* job), checks that Plainday's version files agree and that the lint baseline didn't grow, loads every class file and Templater script the way the plugins do, checks that Plainday's commands and startup scripts name classes that exist, checks the tracked JSON, fails on any tracked file that names a numbered folder the vault dropped (`checkFolders.mjs`, OBS-81), scans the diff, commits, title, body and branch name for the patterns the "Privacy" rule names, and checks the PR body:
  - it links its Linear issue (`Closes OBS-N`, a list such as `Closes OBS-N, OBS-M`, or `Part of OBS-N`; see below), and
  - when files under `plugin/` (the class files included), `Templater/`, `Calendar/` or `Templates/`, or `manifest.json`, change, the PR changes `Config/Manual.md` or `README.md`, or has a `## Docs` section saying why neither needs anything.
  - The checks are plain Node scripts in `.github/ci/`; run one locally with the environment variables its header names, and `node --test .github/ci/*.test.mjs` tests them.
- **Issues:** issues are tracked in Linear, not GitHub.
  - A branch named `<user>/obs-N-<slug>` and a `Closes OBS-N` line in the PR description link the PR and close the issue when it merges.
  - `Part of OBS-N` links without closing. Put a PR like that on a branch without `obs-N` in its name, since the branch name alone would close the issue.
  - **Example issue numbers are `OBS-N`, never real ones.** Linear closes every issue named after `Closes`, `Fixes`, `Resolves` or `Completes` (or another form of those words) in a PR's description or commit messages when it merges, even inside backticks or in an example. A real number written that way closes its issue unbuilt; two issues were lost that way for a month (OBS-65 and OBS-66, by PR #19). To name an issue without closing it, write `Part of OBS-N`, or leave the keyword off.
  - Don't set Linear statuses by hand.
  - **Clusters:** an agent working on an issue may take on a linked issue in the same PR when that saves real work. Review and the one-at-a-time dev vault are the slow part, not building, so a bigger PR only helps when it replaces two of them. All of these must hold, or the issue is left alone and named in the PR as a possible follow-up:
    1. **Same code:** it changes the same script or function, so doing it separately would redo or conflict with this work. A "related" link on its own isn't enough.
    2. **Nothing to decide:** it has no open questions left for the maintainer.
    3. **Free:** it isn't In Progress, assigned or delegated to someone else, and no open PR or branch names it or changes the same files.
    4. **One sitting:** the combined test plan still fits in one test round.
    5. **Said first:** a comment on each issue says it's joining the cluster, and why, before the work starts.
  - **A cluster the maintainer chose:** when the issue's Linear milestone has a description that starts with "One PR", that milestone is the PR. Take its other open issues in too. *Same code* and *One sitting* are settled by that choice; *Nothing to decide*, *Free* and *Said first* still hold, and an issue that fails one stops the work until the maintainer answers. The issue the work starts from carries an area label or `Takes:` line that covers every issue in the milestone. Other milestones (a phase, a release) only group issues.
  - A cluster's PR closes every issue in one line, `Closes OBS-65, OBS-66` (CI reads the list), and its branch carries only the main issue's number.
- **After a merge:** pull the change into this folder (`dev-vault.sh done` does, if a test was in progress), then install it in any vault that uses the system with the **UpdateObsidianPM** command (see README). The command refuses unless the clone is on `main` with a clean tree, so a half-tested branch can't be installed. A personal vault is never a git copy of this repository, because the sample notes' paths would collide with real notes. `CLAUDE.local.md` has the rest of the close-out, if there is any.

## Sample notes

- Every name, client, person, amount, event and date in the sample notes is invented. Keep it that way.
- The notes are there to show every feature. When a feature changes, update the notes that show it.
- Opening the vault runs `TimeReportOnStartup`. If the committed report blocks match what the scripts render, it changes nothing, and `demoVault.test.mjs` checks exactly that. Otherwise opening the vault rewrites tracked notes.

## Tables in notes: keep them out of lists (RULE)

Obsidian doesn't render a table inside a list item: indented under a bullet, it shows as plain pipes. When a note needs a table:

- Start every row at the left edge, with no indent, and leave a blank line before and after the table.
- Put the table after the list, not under a bullet. A bullet can introduce it (`- **Settings:**`), then the table follows at the left edge. Bullets after it start a new list, which renders the same.
- Include the separator row (`|---|---|`) with one cell per column, and give every row the same number of cells.
- Escape a `|` inside a cell as `\|`, including in wikilink aliases (`[[Note\|alias]]`).
- Copy pasted from terminal output often comes indented by two spaces; remove that indent before writing it into a note.

The time reports follow this already: TimeReport writes its tables at the left edge and escapes the `|` in every link.

**Every table a script writes goes through `TimeReport.table` (RULE, OBS-184).** It pads a table the way Obsidian's table editor does, so entering the table changes nothing. A table written any other way gets padded by Obsidian on the first visit, which saves the note; the time report then sees its block as changed and writes it back, on every visit. That covers the reports, timesheets, invoices and any table added later: build the header, the alignments and the rows' cells, and let `table` write the lines. `tables.test.mjs` fails on a row built by hand (`join(" | ")`, or a string starting `| `), and `demoVault.test.mjs` checks that every table in the sample notes' reports, timesheets and invoices is already padded. Tests about what a table says can read it back compactly with `tests/tables.mjs`.

## Privacy: nothing personal reaches GitHub (RULE)

This repository is public. That covers:

- commit messages, PR titles and descriptions, and branch names (shorten Linear's suggested names, which copy the issue title)
- code comments, tests, fixtures, sample notes and any new file

Never include anything from a real vault: note names, people's names, clients or projects, dollar amounts or rates, calendar events, journal or health details, emails, usernames, paths under a home folder, or tokens.

- Refer to real things generically: "a log note", "a client project", "a synced event".
- Write sample notes, test fixtures, comments and PR text from how the system behaves, never from a real note, and don't disguise real data either, such as keeping a real project's initials or a real rate. A bug seen in a real vault is reproduced with an invented note of the same shape; if only the real line will do, it goes in a `*.private.*` test, which git ignores.
- CI scans the diff, commits and PR text for what a pattern can catch: home-folder paths, emails, tokens and claude.ai links. Names, clients and amounts it can't know, so before pushing, read the diff for those yourself.
